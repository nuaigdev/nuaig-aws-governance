# S3 Governance Portal — Project Instructions

## What this is

A production-grade, multi-tenant S3 access-management portal. This is **not a demo or
prototype** — build it to the same standard as a real client deliverable: clean
architecture, proper error handling, no placeholder/lorem-ipsum UI states, no shortcuts
that would need to be rebuilt later. It will first be deployed to our own AWS account to
demonstrate capability, then to a client's account for the same purpose. Assume every
screen may be seen by a client evaluating whether to trust us with their data.

Built by **Nuaig**. This app will be reused across multiple clients — every client-facing
detail (name, logo, buckets, groups) must come from configuration, never be hardcoded.

## Commands

`NEXT_PUBLIC_CLIENT_ID` must be set for every command — config resolution throws
without it. Use `nuaig-internal` for local work.

```bash
npm run dev                  # Next dev server (Turbopack)
npm run build                # production build
npm run verify               # typecheck + lint + test — run before committing
npm run typecheck            # tsc for the app AND amplify/ (separate tsconfigs)
npm run lint                 # eslint
npm test                     # node:test via tsx
npm run sandbox              # ampx sandbox — deploys a personal backend
npm run sandbox:delete
npm run seed:showcase        # synthetic sample files; add --dry-run to preview
npm run prepare:buckets      # client's existing buckets: versioning + CORS (--dry-run first)
```

Run a single test file, or one test by name:

```bash
node --import tsx --test config/access.test.ts
node --import tsx --test --test-name-pattern "never allows a destructive action" \
  amplify/shared/bucket-policy.test.ts
```

### Deploying a sandbox — known pitfalls (all hit in practice)

- Run with `NEXT_PUBLIC_CLIENT_ID` set and `--profile <aws-profile>`; first use in a
  region needs `npx cdk bootstrap aws://<account>/<region>`.
- `amplify/` and `config/` each carry a `package.json` with `"type": "module"`. ampx
  loads the backend through tsx as ESM; without them, imports outside `amplify/`
  fail to resolve (on Windows, in a particularly confusing way). Import `config`
  as `config/index`, never the bare directory.
- Functions need an explicit `resourceGroupName` (`auth` for the Cognito trigger,
  `data` for resolvers), and nothing in the auth stack may reference the data
  stack — otherwise CloudFormation reports a circular dependency.
- **Express mode trap.** For non-hotswappable changes, the sandbox falls back to a
  CloudFormation *Express* update, which re-applies the user pool whenever the
  post-authentication Lambda changes — and the user pool's update handler rejects
  Amplify's schema ("Invalid AttributeDataType input"). A stack that fails in
  Express mode can then only be updated in Express mode. Branch deployments use
  standard mode and are unaffected. If a sandbox gets stuck this way, the
  practical fix is `npm run sandbox:delete` and a fresh deploy.
- Sandboxes force DESTROY on all resources, including the buckets — see
  `docs/no-destructive-actions.md`.

Tests are `node:test` + `node:assert/strict`, run through `tsx` — Node's own ESM
resolver will not resolve the extensionless TS imports. Test files sit beside the code
as `*.test.ts`.

## Architecture

**`config/` is the root of everything.** `config/index.ts` resolves one `ClientConfig`
from `NEXT_PUBLIC_CLIENT_ID` and validates it on import, so a bad config fails the build
rather than surfacing as an empty file list in production. `config/access.ts` is the
single implementation of "what can this user reach" — used by both the UI (what to
render) and `amplify/backend.ts` (what IAM policy to generate). If those diverged, the UI
would advertise access the infrastructure does not grant. Keep them on one implementation.

**Two TypeScript projects.** The root `tsconfig.json` excludes `amplify/`, which has its
own (Node/CDK target, plus the `$amplify/*` path). `npm run typecheck` checks both.
The `$amplify/env/*` modules that `ampx` generates at deploy time are checked in under
`.amplify/generated/env/` (type definitions only, nothing account-specific) so a fresh
clone typechecks before any deploy; ampx overwrites them on each deploy.
`amplify_outputs.json` is gitignored; `scripts/ensure-amplify-outputs.mjs` writes a
marked placeholder on `predev`/`prebuild` so the app builds, and fails loudly at runtime
instead of erroring opaquely on the first network call.

**Access is enforced by IAM, not by the app.** Each Cognito group gets a role whose
policy is generated by `amplify/shared/bucket-policy.ts`, and every group role carries a
permissions boundary capping it at the configured buckets. The UI's checks decide what to
render; the boundary is the security boundary.

**Group access is editable at runtime via scoped IAM** — the `admin-groups` Lambda holds
`iam:PutRolePolicy` over the group roles only, and never accepts policy JSON from a
caller. Read `docs/decisions/group-management.md` before touching that path. Creating a
*new* group still requires a config change and a deploy, and the reason is in that doc.

**The audit log is append-only and written server-side.** No caller has create/update/
delete on `AuditEvent`, including admins. `LOGIN` comes from a Cognito
post-authentication trigger; admin events are written inside their own mutation handlers;
only file-access events originate in the browser, via a handler that refuses any
non-data-access action. Known gaps are documented in `docs/audit-coverage.md`.

**Auth UI is hand-built** on `aws-amplify/auth` — `src/lib/auth/flow.ts` maps Cognito's
challenge states onto a closed union so every state is handled explicitly.
`@aws-amplify/ui-react` is deliberately not a dependency; the design system is too
specific for the Authenticator to match without fighting it.

**Data loading** goes through `src/lib/useAsyncData.ts`, which handles stale-response
ordering and unmount. Don't hand-roll fetch-in-effect — the React Compiler lint rules
reject the naive form, and the hook exists because of it.

## Tech stack

- Next.js (App Router, TypeScript)
- AWS Amplify Gen 2 — code-first (`defineAuth`, `defineData`, `defineStorage`); no Gen 1
  CLI patterns
- Cognito User Pool + Identity Pool (auth, temporary scoped credentials — no static AWS
  keys anywhere in the app)
- DynamoDB via Amplify Data (portal metadata, audit log)
- Amplify Functions (Lambda) for all admin operations (user/group management)
- S3 via Amplify Storage (client buckets)

## Multi-tenant client configuration

Each client gets its own config file under `config/clients/<client-id>.ts`:

```ts
export const clientConfig = {
  clientId: "acme-senior-living",
  displayName: "Acme Senior Living",
  logo: "/branding/client-logo.svg", // client's own logo if provided, else omitted
  buckets: [
    { id: "documents", label: "Documents & Images", bucketName: "acme-documents" },
    { id: "pii", label: "Resident & Customer Data", bucketName: "acme-pii" },
    { id: "financial", label: "Financial Records", bucketName: "acme-financial" },
    { id: "clinical", label: "Clinical Records", bucketName: "acme-imar" },
  ],
  groups: [
    { id: "admin", label: "Administrator", bucketAccess: [{ bucketId: "*", mode: "read-upload" }] },
    { id: "documents", label: "Documents Team", bucketAccess: [{ bucketId: "documents", mode: "read-upload" }] },
    { id: "pii", label: "PII Access", bucketAccess: [{ bucketId: "pii", mode: "read" }] },
    { id: "financial", label: "Finance Team", bucketAccess: [{ bucketId: "financial", mode: "read" }] },
    { id: "clinical", label: "Clinical Staff", bucketAccess: [{ bucketId: "clinical", mode: "read" }] },
  ],
}
```

The active client is selected via an environment variable (`NEXT_PUBLIC_CLIENT_ID`) at
build/deploy time — one deployment serves one client's config. Nothing in components or
pages should reference a client name, bucket name, or group directly; always read from
this config. Our own showcase deployment uses a `nuaig-internal` config with realistic
mock data (see below).

### Access modes

`bucketAccess` is an explicit grant list, never a bare string array — it maps 1:1 onto the
IAM policy generated for the group's role, so policy generation stays a direct
translation rather than an interpretation.

```ts
type AccessMode = "read" | "read-upload"
type BucketGrant = { bucketId: BucketId | "*"; mode: AccessMode }
```

- `"read"` — `s3:GetObject` + `s3:ListBucket`.
- `"read-upload"` — the above plus `s3:PutObject` for **new keys only**. Never
  `s3:DeleteObject`, `s3:DeleteObjectVersion`, or an overwrite of an existing key.
- `bucketId: "*"` is the admin grant, matching the IAM wildcard idiom.

The mode is named `read-upload` and not `read-write` on purpose: "write" is the word that
invites someone to quietly add a delete path later. The mode name states its own ceiling.
See **Critical constraint** below.

## Design system

Light theme only — no dark mode toggle anywhere in the app.

**Color tokens** (base palette — deliberately not blue, orange, or green, to sit apart
from our logo's own cyan accent and from generic SaaS defaults):
```
--bg:            #F7F5F2   /* warm stone page background */
--surface:       #FFFFFF   /* cards, table rows, panels */
--ink:           #171417   /* primary text */
--ink-muted:     #6B6470   /* secondary text, metadata */
--primary:       #4E2A4B   /* deep aubergine — buttons, active nav, focus rings */
--primary-tint:  #EFE4EC   /* hover/active background wash */
--border:        #E4DFDA
--footer-bg:     #171417   /* dark anchor band, pairs with white logo */
```
Status colors (success/warning/error) use conventional, desaturated tones — these are
functional UX signals, not brand color, and are exempt from the above restriction.

**Typography:** IBM Plex Sans for all interface copy and headings. IBM Plex Mono for
every data value — file sizes, timestamps, S3 paths/keys, user/group counts. This split
is structural, not decorative: it visually separates human-readable content from system
data throughout the app.

**Layout:** Header navigation only — no sidebar, ever. Header contains: logo + client
name (left), primary nav (center or left-aligned next to it), user menu (right). Content
area is a centered, max-width container. The S3 browser is a dense, sortable table
(name, size, last modified, uploaded by) — not a card grid; this is a file-management
tool, and a table is the correct density for that job.

**Restraint:** Aubergine is the one bold color in the app — used sparingly (primary
buttons, active states, focus rings) against an otherwise quiet, neutral interface. Don't
decorate beyond that. No gradients, no drop-shadows-on-everything, no unnecessary badges.

## Deployment readiness

Status of the path to a client deployment. Keep this current — the point is that
deployment day needs no assessment.

- **Runbook:** `docs/deployment-plan.md` is the single source. It covers what the
  client must provide (no AWS knowledge required of them), bucket preparation,
  deployment steps with a check after each, the smoke test, and handover.
- **Deployment model:** the client has no AWS admin. They provision one temporary
  admin identity; Nuaig deploys and the client then deletes it. The client's four
  buckets already exist — `bucketProvisioning: "existing"`, **never created**.
- **Hosting:** Amplify Hosting on the default `amplifyapp.com` URL (managed HTTPS).
  No custom domain, no certificate work.
- **Bucket preparation is scripted:** `npm run prepare:buckets` (use `--dry-run`
  first). It enables versioning and merges in the portal's CORS rule on the
  client's imported buckets, and reports public-access / SSL status without
  changing them. It never deletes, never writes objects, never touches bucket
  policy or encryption. It needs the live URL, so it runs after the first build.
- **Scope decisions made with the client (do not re-litigate):** buckets are not
  encrypted with KMS; uploads are rare, so no upload size/type limits or
  overwrite-race work beyond versioning; no Cognito advanced security; no custom
  domain; compliance is covered by the existing BAA, so notices are generic and
  platform-level, not client-authored legal text.
- **Sessions:** 30 min idle sign-out in the UI, short access tokens, 12 h refresh.
- **Admin password reset** exists (Users page → Reset password), audited as
  `USER_PASSWORD_RESET`.
- **Before go-live checklist:** `npm run verify` green; client config registered
  with the real bucket names; client logo in `public/branding/` (or accepted as
  text); `docs/deployment-plan.md` Part C followed in order.

## Roles and groups (define from the start)

Every client config always includes an `admin` group with access to all buckets, plus
one or more scoped groups mapped to specific buckets, as shown above. Group membership,
not individual per-user grants, is the only way access is assigned — this must hold from
the very first user created, not retrofitted later. A user can belong to multiple groups.

## Features — all managed from within the app

1. **Authentication** — Cognito-backed login, MFA required for all users (not just
   admins) given the sensitivity of the data types involved.
2. **User management (admin only)** — create user (Cognito `AdminCreateUser` + assign to
   group(s) + send invite), disable/offboard user (`AdminDisableUser` + revoke active
   sessions), list users with their groups and last login.
3. **Group management (admin only)** — create/edit groups and their bucket-access
   mapping, without needing to touch AWS IAM directly.
4. **Bucket browser (all users)** — each user sees only the buckets their group(s) grant
   access to, per the client config. View, search, and download files. Upload is allowed
   for groups holding a `read-upload` grant on that bucket.
5. **Audit log (admin only)** — every login, file view/download, upload, and admin
   action (user/group change) recorded in DynamoDB: who, what, when, which bucket.
   Searchable and filterable in the UI.

## Critical constraint: no destructive actions

Per the client's own stated concerns (accidental loss, tampering), **this app must not
expose any delete or overwrite capability, for any role, including admins** — not a
hidden admin-only delete, not a "soft delete," none. Deletion of objects, versions, or
buckets happens only through deliberate, out-of-band AWS operations (lifecycle policies,
direct console/CLI action by whoever manages the AWS account), never through this UI.
Uploads must never overwrite an existing key silently — reject or auto-version on
collision. Flag in code review if any planned feature would introduce a delete/overwrite
path, rather than assuming it's fine because a role is "trusted."

## Data-protection notices

Short, generic and platform-level — the client does not author them and there is
no Privacy Notice / Acceptable Use page. Placement: sign-in page (authorised use,
activity logged), a slim banner above `sensitive` buckets, the upload dialog
(only upload what you are authorised to share; nothing can be deleted afterwards),
and one line in the footer. Copy lives in `src/lib/notices.ts`, not inline.

## Mock data for our internal showcase

Do not mimic any real client's actual bucket names or data. Build a generic, realistic
mock environment (`nuaig-internal` config) with 4 buckets and sample synthetic files
(documents, sample PII-shaped records, sample financial-shaped records, sample clinical-
shaped records — all clearly fake) so the showcase demonstrates the real shape of the
product without resembling any specific client's environment.

## Security

- No static AWS credentials anywhere in the codebase or environment — Cognito Identity
  Pool issues temporary, scoped credentials per session.
- Least-privilege IAM throughout: each group's role can reach only its configured
  bucket(s), nothing else.
- Every admin action and data access is logged (see Audit log above) — no silent
  operations.
- Flag, rather than silently assume, any place a real deployment needs a decision not
  specified here (session duration, password policy specifics, invite email content).
