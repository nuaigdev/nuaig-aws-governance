# Decision: runtime group access editing, via scoped IAM

**Status:** accepted
**Date:** 2026-09-18

## Context

Two requirements in `CLAUDE.md` pull against each other:

- **Feature 3** — administrators create and edit groups and their bucket-access
  mapping from inside the portal, "without needing to touch AWS IAM directly".
- **Security** — "each group's role can reach only its configured bucket(s)",
  i.e. enforcement by per-group IAM roles with temporary scoped credentials.

Honouring both means the portal must write IAM policy at runtime. That gives a
Lambda in this application permission to rewrite its own access controls, which
is precisely the capability an attacker would want.

## Options considered

1. **Config + redeploy.** Group definitions live in the client config; changing
   access is a reviewed commit. IAM stays static. Safest, but does not meet
   Feature 3.
2. **Runtime editing via IAM.** The admin Lambda holds `iam:PutRolePolicy` over
   the group roles. Meets Feature 3 literally.
3. **Runtime editing, server-side enforcement.** Mapping moves to DynamoDB and a
   Lambda mints presigned URLs per request. Fully dynamic, IAM stays static —
   but abandons the "scoped credentials per session" model the spec calls for.

## Decision

**Option 2**, with four guardrails that bound the privilege. All four are
load-bearing; weakening any one of them should be raised in review.

1. **Resource scoping.** The `iam:PutRolePolicy` / `DeleteRolePolicy` /
   `GetRolePolicy` grant in `amplify/backend.ts` names only the Cognito group
   role ARNs. The function cannot touch its own execution role, the admin role,
   or anything else in the account.

2. **No policy JSON from callers.** The `manageGroups` mutation accepts only
   `(groupId, bucketId, mode)` tuples, each validated against the client config.
   The document is generated by `buildBucketPolicy`, which has no branch that
   emits a destructive action. A caller chooses from a closed set; they never
   supply IAM for us to apply.

3. **Permissions boundary.** Every group role carries a boundary capping it at
   the configured buckets, denying all destructive S3 actions and `iam:*`. A
   boundary is an intersection, so a policy written at runtime can only narrow
   what is already permitted — never exceed it.

4. **No attach, no create.** The grant deliberately excludes
   `iam:AttachRolePolicy` (which could bind `AdministratorAccess`),
   `iam:CreateRole` and `iam:PassRole`.

## What still requires a deploy

**Creating a new group.** A new group needs a new IAM role, which means
`iam:CreateRole` and `iam:PassRole`. Those cannot be pre-scoped to a role that
does not exist yet, so granting them would reopen the escalation path guardrails
(1) and (4) close.

New groups are therefore a client-config change plus a deploy — reviewable and
version-controlled. What is available at runtime:

- editing an existing group's bucket access (this portal), and
- moving users between groups (`admin-users`).

The admin group additionally cannot be narrowed from the UI at all; it is the
portal's way back in, and stranding it would leave no in-app route to recover.

## Consequences

- The Groups screen shows **live IAM** as the source of truth, and flags a group
  whose access has diverged from what the config declares.
- Every change is audited as `GROUP_ACCESS_CHANGED`, recording the previous and
  next access and the role written to.
- A compromise of the `admin-groups` Lambda can reshuffle access **among the
  configured buckets**, but cannot reach any other bucket, grant deletion, or
  escalate its own IAM.
